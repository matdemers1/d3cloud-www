# CLAUDE.md — d3cloud-www

Home of the **D3 Cloud** ecosystem at `d3cloud.io` — *Demers Design and Development* is the maker's line under it (DI-ADR-006). Single-page React SPA. **No backend, no database, no auth.** Same stack and Worker pattern as [`d3-qr`](../d3-qr/); styled with the D3 Cloud design system, `@d3cloud/ui` (ADR-005).

Read this before doing any work. The plan lives in Foreman as project `DI` — start with `foreman_brief DI`.

## Key Conventions

- **No backend, ever.** Pure static SPA. See `ADR-001 — Static SPA on Cloudflare Workers`.
- **Lightweight hand-rolled router** (`src/router.tsx`, History API, no dependency) for per-app pages: `/clearwhen`, `/clearwhen/privacy|terms|support`, same under `/qr`; `/ui` has a project page only — pages without legal docs get no privacy/terms/support links or route. See `ADR-004` (supersedes `ADR-002`). **Still no routing library.**
- **No analytics, no telemetry on this site.** CSP `connect-src 'self'` enforces it. (This is *not* a public stance about future projects.)
- **Styled with `@d3cloud/ui`** (ADR-005, supersedes "mirror d3-qr"). Installed from the GitHub release tarball — the package lives in a subdirectory, so a git-tag install fails. Use its semantic utilities (`bg-surface`, `text-fg-muted`, `text-14`, `rounded-lg`) and components (`Card`, `Badge`, `Link`). `npm run lint` runs `d3-check-usage src`: no raw hex, palette classes, off-scale values or shadows. A genuine exception needs `d3-allow: <reason>` on or above the line.
- **Spacing goes on a wrapper, never on a library component.** Before 1.2 the components' CSS arrived unlayered and beat Tailwind utilities, so `<Card className="mb-8">` silently did nothing; 1.2.2 puts it in `@layer d3-ui`, below utilities, but the rule stays — a wrapper survives either way.
- **Interface type follows the system scale (11–24px); display headings use the site's display layer** (DI-ADR-006): `font-display` (Instrument Serif) with `text-display-sm|md|lg|xl` and `text-stat`, all defined in `src/styles/index.css`. Never an arbitrary size at a call site.
- **The ecosystem is declared, not drawn.** Each project in `projects.ts` has a `kind` (`ecosystem` | `fix`), a `star` position and its `relations` (`signs-in-with`, `built-on`, `planned-in`). The hero, the map, the link-preview card and each product page's "In the constellation" block read them through `src/content/ecosystem.ts`, which also holds the build log and the workshop list. A new product is a new entry there — tests fail on a relation to an unknown project.
- **Projects on the bench get workshop pages, not product pages** (DI-REQ-037/038). `WORKSHOP` in `src/content/ecosystem.ts` holds each one's stage, an honest stage note, and features each marked `built` or planned — only what the project's own plan and live site support. They are not stars on the map and not in either of the two kinds; when one launches it moves into `PROJECTS`. A screenshot of what is live goes in `public/screenshots/<slug>/`; with nothing public to show, a drawing in `src/components/WorkshopArt.tsx`. Link only to what a stranger can use today — a repo, never an instance still being set up.
- **Motion is CSS only, and none of it runs under `prefers-reduced-motion`** (DI-REQ-032) — the kill switch is in `index.css`. Every animation must end at a complete resting state.
- **The mark is the planisphere** (`src/components/Logo.tsx`, `public/favicon.svg`, the OG card in `scripts/generate-static.ts`). On a product page its lit star takes the product's colour.
- **Each product has its own mark** (DI-REQ-040) — the ring family chosen on the *Brand & Site Concepts* canvas on 2026-09-25, in `src/components/ProductMark.tsx`: the planisphere's ring, ink lines, one lit star in the product's accent. Auth is Keyhole, UI Compass, Shipyard Lift-off, Foreman True North, Bindery Dog-ear, Postroom Envelope (orchid, DI-T-9.1), Floorspec Junction and D3 Floorspec Door swing (both chartreuse, DI-T-10.1; `npm run icons:floorspec` exports the app's favicon and PWA icons to the gitignored `scripts/out/`). Clearwhen uses its App Store icon (`public/marks/`); a product with neither falls back to the planisphere. It shows in the product hero and the header crumb.
- **A product page can carry a deep dive** (DI-REQ-039): `src/pages/deep/<Product>.tsx`, registered in `src/pages/deep/index.ts`. It owns its sections and their order; the page supplies the hero and the closing sections. Build it from `src/components/Deep.tsx` (`DeepIndex`, `DeepSection`, `Figure`, `Stat`, `BarRow`, `FlowDown`), draw every chart and diagram in code from tokens, keep a product's accent to marks and bars (it fails contrast as text in the light theme), and make every number traceable to the product's repo or its Foreman records. Foreman's is the pattern.
- **The Floorspec standard is published here** (FLR-ADR-018, DI-REQ-042): `/floorspec`, `/floorspec/<spec>/<chapter>` for every specification that has chapters (Core, Ops and Rules — `/floorspec/core/walls`, `/floorspec/ops/references`, `/floorspec/rules/measures`), `/floorspec/coverage` (all of them), the extension registry at `/floorspec/registry` and `/floorspec/registry/<NAME>`, each library at `/floorspec/library/<name>` and `/floorspec/library/<name>/<version>`, and D3 Floorspec's workshop page at `/floorspec/app` (a `WorkshopItem` may declare its own `path`). **The current draft lives at the unversioned URL; every earlier draft stays at `/floorspec/<spec>/<version>/<chapter>`** (DI-T-10.7 — Core 0.4, Ops 0.4 and Rules 0.2 current, from 244d8b3; Core and Ops 0.3 and Rules 0.1 at `/floorspec/core/0.3/…`, `/floorspec/rules/0.1/…` from 8a99d02, Core and Ops 0.2 from 6f9bc07, 0.1 from 3bf4f35), `/floorspec/<spec>/<current version>/<chapter>` 301s to the unversioned page, and a statement ID a draft retired (its chapter 0 "Changes from" tables) gets a note in the current chapter, with that ID as its element id, naming the draft that retired it, pointing at the replacement — followed to the current statement when a table names one a later draft retired in turn, though the standard now rewrites its earlier tables to name the newest (Core 0.4: 1.2.1 → 1.2.7) — and at the earlier draft that had it. A row with a dash for its replacement (Core 0.4's `FS-CORE-17.7.2`) was retired with nothing in its place, and its note says only why. Tests take which draft is current from the lock, never from a literal, so the next sync does not break them; what a draft *is* — its chapters, its retired IDs, its commit — they assert. The landing page's "What <version> adds" lists the chapters no earlier draft had, read from the index, and what `CHANGED` in `pages.tsx` says a draft changed in chapters it kept — hand-written from its "Changes from" section and keyed `<spec>@<version>`, so a note disappears rather than goes stale when its draft is superseded: add the next draft's when you sync it. `npm run sync:floorspec [-- <checkout>]` (default `../floorspec`) refuses a dirty `spec/`, `schema/`, `conformance/`, `registry/`, `library/` or `rules/`, pins the commit and each specification's draft version (the `**Draft n.n` in its README) in `src/floorspec/floorspec.lock.json` — when a version moves on, the commit the lock last pinned for it is kept under `earlier` and that draft is rebuilt from it with `git archive` (never from the working tree), so never hand-edit or drop an `earlier` pin — parses each chapter with marked's lexer into the JSON AST of `src/floorspec/ast.ts` (rendered by `Prose.tsx` — no HTML strings), and writes `src/floorspec/generated/`: `index.json` (what the routes need — kept small, it is in the entry bundle), `<spec>/<version>/chapters/*.json` (with the chapter's source path and its retired-ID notes) and `coverage.json`, `registry/index.json` (every `registry/<NAME>/extension.json` with its evidence, recorded exceptions, suite counts and the registry README), `registry/<NAME>.json` (its `spec.md`, chapters as `#chapter-<n>` anchors, statements in its own ID space — `#FS-ELEC-3.1.1`), `libraries.json` and `packs.json` (the rule packs in `rules/`). All of it is committed so CI never needs the checkout; nothing is written until everything has been read and checked. Never hand-edit generated files. Chapter text, coverage, the registry and the libraries load as their own chunks (`src/floorspec/pages.tsx`, `registry.tsx`). Coverage comes from the repo's own gate when its dependencies are installed, otherwise a scan of the suites the gate counts (`conformance/<spec>/<version>/`, plus `conformance/migration/<version>/` for Core). Statement IDs are element ids (`/floorspec/core/walls#FS-CORE-5.3.1`, `/floorspec/rules/rules#FS-RULES-3.9.1`); section numbers are heading ids (`#5.3`). A bare number links within its own specification; one named for another (`Core §5.3`, `Core 5.2.1, 5.2.2`) links to that specification at the same commit. A Markdown link to something the site publishes — a chapter, `registry/<NAME>/spec.md`, a schema, a library file — becomes its address here; anything else, GitHub at the pinned commit.
- **A published schema or library URL never changes.** The sync copies every `schema/<name>/<v>/*.json` (each specification's drafts, and `registry/0.1`) byte for byte into `public/floorspec/schema/<name>/<v>/`, and each extension's `registry/<NAME>/*.schema.json` to the path its own `$id` names (`/floorspec/schema/ext/<NAME>/<version>/<short>.schema.json` — read from the file, never constructed), recording each SHA-256 in `src/floorspec/published-schemas.json`. A draft that changes no schema publishes none of its own: Ops 0.4's requests match `schema/ops/0.3/`, as `spec/ops/01-transactions.md` says, so there is no `schema/ops/0.4/`. Libraries go to `public/floorspec/library/<name>/<version>/`, byte for byte, recorded in `src/floorspec/published-libraries.json`: `library/<name>/<version>/` (manifest `index.json`, whose `library` URL gives the name — the US starter library is at the URL it names) and an extension's `registry/<NAME>/library/` (manifest `library.json`, named after its `extension` — FS_furniture's names no URL, so the site chose `/floorspec/library/FS_furniture/<version>/`); every file a manifest names, its `sha256`/`byteLength` and any `SHA256SUMS` are checked. The sync refuses to change a recorded file or to drop a specification's schema; an extension's or library's earlier version leaves the checkout when the registry moves on and stays in `public/` as recorded (its listing is carried forward). Tests hold `public/` to both records. A changed file is a new version directory. The Worker serves `/floorspec/schema/**` and every file under `/floorspec/library/<name>/<version>/` (a `SHA256SUMS` too, as text) with `Access-Control-Allow-Origin: *` and a one-year `immutable` cache, and resolves pages before files — `/floorspec/library/us-starter/0.1.0` is a page although it looks like one. Only export handlers or objects from `src/worker.ts` — workerd refuses to start on a string export.
- **The playground runs the reference engine in the browser** (FLR-T-10.2, FLR-REQ-137): `/floorspec/playground` validates a dropped `.json` document or `.floorspec` package (a ZIP holding `model.json` and its assets) with D3 Floorspec's own engine and reader (`OFFICIAL_READER`), draws each level with its plan renderer from that one evaluation (`renderEvaluation`, which never validates — so a file is validated once, however often its plan is redrawn, and a document that requires an official extension draws; a test counts the calls; an SVG shown as a blob-URL `<img>`, never parsed into the page; a document with errors gets its walls' lines as written instead), meshes it in 3D with its mesher (manifold-3d WASM) and three.js, and lists every diagnostic exactly as the engine reports it. The file never leaves the page — nothing fetches or stores it — and nothing in it says "compliant". The engine is **vendored, not installed**: `npm run sync:playground [-- <checkout> [<commit>]]` (default `../d3-floorspec` at its `origin/main`) reads the commit with `git archive` into a temp dir (never the working tree), installs it there with its own lockfile, builds `@floorspec/engine`, `render2d`, `package` and `mesh` with their own build, and bundles the surface the playground uses with esbuild into `vendor/d3-floorspec/` (`engine.js`, `mesh.js`, shared chunks, `manifold.wasm`, hand-written `engine.d.ts`/`mesh.d.ts` from `scripts/playground-dts.ts`, licences), plus the standard's starter templates byte for byte from the Floorspec commit `src/floorspec/floorspec.lock.json` pins; `vendor/d3-floorspec/lock.json` records both commits and every file's SHA-256, and a test holds the files to it — so moving the standard's pin means re-running `sync:playground` (with `FLOORSPEC_DIR=<checkout>` when the pinned commit is not in `../floorspec`). The output is reproducible run to run. It pins d3-floorspec 1f12f93 (FLR-T-12.8: render2d's `renderEvaluation`/`sceneOf` take an evaluation, and `renderPlan` defaults to `OFFICIAL_READER`), whose `@floorspec/engine` 0.4.0-draft reads Core 0.1 to 0.4 — arcs, winders and spirals, the weighted roof skeleton — with its samples from floorspec 244d8b3. manifold-3d's embind compiles its binding wrappers with `new Function` at start-up; the sync swaps those two spots for the closures Emscripten builds with `DYNAMIC_EXECUTION=0`, refuses if either no longer matches exactly once, and refuses unless every template meshes identically with and without the patch. Never hand-edit `vendor/`. The page, the engine, the 3D view (mesher + three.js) and each sample are separate lazy chunks; none of it is in the entry bundle.
- **The playground has its own CSP, and only it.** `src/worker.ts` serves `/floorspec/playground` with `PLAYGROUND_HEADERS`: the same headers with `script-src 'self' 'wasm-unsafe-eval'` (WebAssembly compilation only — never `'unsafe-eval'`); every other page and every file keeps `SECURITY_HEADERS`, and `connect-src 'self'` holds everywhere. `hasOwnPolicy` in `routes.ts` names such pages, and the router reaches or leaves one with a full page load, because a document keeps the policy it was loaded with.
- **In-app navigation uses `Link` from `src/router.tsx`** (wraps the library `Link`) or `useNavigateOnClick` on a library `Card href`.
- **Screenshots live in `public/screenshots/<slug>/`** as WebP with their real width/height recorded in `projects.ts`.
- **Apex Custom Domain only — never a wildcard route.** A wildcard `*.d3cloud.io/*` would break `qr.d3cloud.io`.
- **Theme storage key is `d3cloud-theme`** (not `d3qr-theme`). `ThemeProvider` (in `main.tsx`) and the header's `ThemeSwitch` own it; `public/theme-init.js` is `themeBootScript('d3cloud-theme')` from the library, kept as a file because CSP blocks inline script, and `src/site.test.ts` fails if the two differ.
- **`src/routes.ts` is the one list of pages.** The app, the Worker and the sitemap all read it. A new page is a new entry there, not a new branch in three places.
- **Per-page `<head>` comes from the Worker.** `src/head.ts` renders title, description, canonical, Open Graph and Twitter tags; the Worker swaps them into index.html between the `route-meta` markers. index.html carries the home page's block, and a test holds it equal to `renderHead('/')` — change `head.ts`, then paste its output back.
- **Fonts are Inter and JetBrains Mono, self-hosted by `@d3cloud/ui`, plus Instrument Serif from `@fontsource/instrument-serif`** (Latin, 400 normal + italic, imported in `main.tsx`) — all same-origin, so `font-src 'self'` holds.
- **Bundle budget: 150kb gzipped.** ~147.5kb after the playground (FLR-T-10.2 — all of it lazy), ~147.7kb after Floorspec 0.3 (DI-T-10.6 — the Floorspec index the routes need lists every published draft, extension and library, so retired-ID notes and chapter source paths live in each chapter's JSON instead; chapter text, coverage, the registry, the libraries and the pages stay lazy chunks), ~148.9kb after Floorspec 0.4 (DI-T-10.7 — 147.6 with the 0.3 index, so the three drafts that became earlier ones cost ~1.25 kB, ~0.9 of it their chapter summaries, which only the routes' head descriptions read; the next Core/Ops/Rules move will cross the budget unless the earlier drafts' summaries, or the whole earlier list, leave the entry first): the library ships one flat `dist/index.js`, so unused Radix code can't be tree-shaken yet. Measure with `npm run build` (the `index-*.js` line) before and after any change to `src/floorspec/spec.ts`, `routes.ts` or the index the sync writes.
- **No co-author footer in commits.**
- **Deploy via git push to `main`.** GitHub Actions builds and deploys to Cloudflare Workers. Do not deploy by hand — a manual `wrangler deploy` puts a laptop build on the live site that doesn't match `main`.

## Build & Dev Commands

```bash
npm install
npm run dev          # http://localhost:5173
npm run build        # outputs dist/, then scripts/generate-static.ts adds og-image.png, robots.txt, sitemap.xml
npm run preview      # preview the production build
npm run lint         # eslint + d3-check-usage
npm test             # vitest: routes, Worker, head, theme, Floorspec pages, schemas and libraries
npm run sync:floorspec   # regenerate the /floorspec pages from ../floorspec (commit the result)
npm run sync:playground  # re-vendor D3 Floorspec's engine for /floorspec/playground from ../d3-floorspec origin/main (commit the result)
npm run format       # prettier --write .
# Deploys happen in CI: push to main -> .github/workflows/deploy.yml
# npx wrangler deploy   # manual fallback only
```

## Architecture (one-paragraph version)

Every request reaches `src/worker.ts` first (`run_worker_first: true`). A file (anything with an extension) is passed to the Static Assets binding, which answers 404 when it is missing — there is **no SPA fallback** any more, because that returned the home page with a 200 for every typo. A page is looked up in `src/routes.ts`: a real page gets `index.html` with its own head swapped in and a 200; a renamed slug (`/daypart/*`) or a trailing slash gets a 301 to the canonical address; anything else gets the app's not-found page with a **404** and `noindex`. Every response carries CSP (the playground's allows `'wasm-unsafe-eval'`, nothing else does), HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy and COOP. In the browser, the History API router renders the page for the path; theme is the only state.

## Stack

- React 19 + Vite 7 + TypeScript
- Tailwind CSS v4 via `@import '@d3cloud/ui/theme.css'` (brings Tailwind, tokens, fonts, the `dark` variant) + `@source '../'`
- `@d3cloud/ui` v1.2.2
- Cloudflare Workers (Static Assets binding, `run_worker_first: true`)

## What NOT to Do

- Don't add a backend, an API endpoint, or a database
- Don't add `react-router` or any other routing library — `src/router.tsx` is deliberate and sufficient
- Don't change `/clearwhen/privacy`, `/clearwhen/terms` or `/clearwhen/support` — those URLs ship inside the Clearwhen binary and in its App Store listing; add a redirect instead of renaming. `/daypart/*` is kept as a redirect for an early build that shipped the old path.
- Don't add a state management library (Zustand, Redux, etc.)
- Don't add analytics, telemetry, or tracking scripts
- Don't add a wildcard Worker route on `*.d3cloud.io` (would break `qr.d3cloud.io`)
- Don't add `connect-src` exceptions to the CSP, and never `'unsafe-eval'` — the playground's WebAssembly needs only `'wasm-unsafe-eval'`, on that page alone
- Don't add `dangerouslySetInnerHTML` anywhere
- Don't change the theme storage key from `d3cloud-theme`
- Don't touch `qr.d3cloud.io` deployment when working on this project
